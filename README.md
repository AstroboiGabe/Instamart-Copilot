## PART D — Policy RAG Assistant and Refund Agent

- Step 1: Run ``RAGmania.py`` file which breaks all the policy files into chunks and gets vectorized which retrieves relevent output based on the tickets and following the guardrails. ReAct (Reason + Act) is employed as seen in file. Check the output in terminal to see the results of demo runs and to see the number of chunks being created and the tools being called for crash run. It creates agent_runs.jsonl and refund_ledger.jsonl files in output folder.

- **S1 at 5 calls and 1,905 tokens, S5 at 3 calls and 736 tokens, and S6 at 2 calls and 238 tokens. Each observation is added to the context, so token use grows with every step. The model returns the full step list once, for example get_order → search_policy → calculate_refund → issue_refund for S1. Code runs those steps without further model calls, so S1 would need about 2 calls. With ReAct, the model sees NOT_FOUND in S6 and stops after 2 calls. Plan-and-execute has to replan on error, which costs one extra model call, and the executor must check each result. Otherwise it could run calculate_refund on missing data. A cancelled order works the same way: the planned refund step becomes invalid and needs a replan. I would keep ReAct for this refund workflow. Each decision depends on the last observation (order status, delivery time, the INR 1,000 threshold), and ReAct handles that naturally. It is also cheap on short cases like S5 and S6, and the iteration and token limits cap the worst case. Plan-and-execute would suit longer, predictable workflows with independent steps, where its lower token cost matters more.**
